# 02 · 产品规划(v2)

> 基于 01-research-benchmark.md 的调研结论,本文档给出 4Seas CommunityOS 的产品规划。
> v2 更新(2026-09):身份/账户/积分/签到/NFT 统一由外部 Community Account System(CAS)提供;积分默认不收取但预留接口;Luma/Social Layer 先做单向发布;Telegram 通知经 4seasbot;Mini App 二期。详见 06、07 文档。

---

## 1. 产品定位

### 1.1 一句话定位

**4Seas CommunityOS:运营于物理世界的在地社区操作系统——管好场地(Place),驱动活动(Event),服务成员(People)。**

### 1.2 系统边界(重要)

本系统**只管三件事**:场地、活动、预订。以下能力**不在本系统实现**,通过接口调用外部系统:

| 能力 | 提供方 | 说明 |
| --- | --- | --- |
| 账户(注册/登录/验证/会话) | **Community Account System(CAS)** | 邮箱为身份主键;未来支持链上地址登录 |
| 积分(余额/流水/发放/扣减) | **CAS + 链上(未来)** | 数据库只做镜像存储,以链上为准 |
| 活动签到(URL + 签名) | **CAS** | 未来接入外部 NFT 系统自动签发 |
| NFT 签发 | 外部 NFT 系统(V2) | 主持人轮换二维码 + 一次性领取网址 + 数字上限 |
| 邮件发送 | 邮件服务(事务邮件) | 验证码/通知走邮件通道 |
| Telegram 通知 | **4seasbot**(既有服务) | 本系统提供数据,4seasbot 负责推送 |

CAS 仓库:git@github.com:4seas-community/Community-Account-System.git(开源)。接口需求见 [06-community-account-system.md](06-community-account-system.md)。

### 1.3 我们要解决的真问题

4Seas 在清迈运营多栋自运营建筑(Building F、4Seas Nimman 等),当前痛点:

1. **场地信息分散**:楼层、房间、设备、容量、开放时间靠口口相传或表格,没有单一事实源。
2. **场地使用无规则、无 trace**:谁能用、要不要审批、违反什么规则,靠临时协商;占用冲突靠运气。
3. **活动发起链路长**:一场成员自发活动要经过多次沟通才能定场地、发通知。
4. **对外分发靠手工**:活动信息要手工搬去 Luma / Social Layer。
5. **成员身份与贡献无沉淀**:谁参加了什么、贡献了多少,没有可携带的记录(未来由 CAS + 链上积分 + NFT 解决,见 07)。

### 1.4 产品目标(12 个月)

| 目标 | 衡量 |
| --- | --- |
| 场地使用透明化 | 100% 自运营场地在系统内,占用可视(日程表/地图) |
| 活动发起低门槛 | 成员 3 分钟内完成最小活动创建(what/when/where) |
| 对外分发自动化 | 发布后自动单向同步 Luma 与 Social Layer |
| 成员运营闭环 | CAS 注册 → 验证 → 预订/发起 → 签到,全链路线上化 |
| Agent 可用 | 外部 Agent 可通过 MCP/REST 查询场地与活动、按 draft+confirm 流程创建 |

## 2. 目标用户与角色

| 角色 | 描述 | 关键权限 |
| --- | --- | --- |
| Visitor 访客 | 未注册/未验证 | 浏览公开活动页、报名公开活动(留邮箱即创建待验证账户) |
| Member 成员 | CAS 中邮箱已验证 | 发起活动、预订场地(按规则)、报名、签到、收藏 |
| Host 活动发起人 | 成员默认身份,可被场地规则限制 | 管理自己活动的报名、嘉宾名单、签到 |
| Venue Manager 场地管理员 | 管理特定建筑/场地 | 场地 CRUD、规则配置、预订审批、占用调整 |
| Admin 社区管理员 | 社区运营 | 全局配置、成员角色、数据导出、集成管理 |
| Agent 智能体 | 外部 AI Agent(机器身份) | 按 scope 查询;创建类操作走 draft + confirm |

说明:角色数据存在本系统,但身份主数据(邮箱、验证状态、未来链上地址)以 CAS 为准;本系统通过 cas_user_id 关联。

## 5. 核心功能详述

### 5.1 Place:场地管理

**实体层级**:Building(建筑)→ Floor(楼层)→ Venue(房间/场地)。

**场地基础信息(CRUD)**:名称、归属建筑/楼层、编号、地址与坐标、面积、容纳上限(座位/站立)、设备清单、基础服务、开放时间段(按星期)、例外日期、照片、状态(开放/维护中/停用)。

**场地规则(附加于场地,可版本化)**:

| 规则项 | 说明 |
| --- | --- |
| 允许的活动类型 | 白名单(会议/工作坊/课程/派对/展览/运动...) |
| 申请流程 | 自动通过 / 场地管理员审批 / 社区管理员审批 |
| 积分消耗 | **默认 0(不收取)**;字段与接口预留,V2 链上积分对接后启用(见 07) |
| 提前预订窗口 | 最多提前 N 天;最短提前 N 小时 |
| 单次/每月时长上限 | 防囤积 |
| 缓冲时间 | 布置 + 撤场分钟数 |
| 取消政策 | 提前多久免费取消,逾期处理方式 |
| 禁止行为 | 明示条款,预订时须确认 |
| 准入要求 | 仅验证成员 / 特定角色 / 公开 |

**原则**:规则是"可编辑的层",不是硬编码;规则变更留存版本,不影响已确认预订。

### 5.2 Event:活动生命周期

**状态机**:draft → preview →(需审批时)pending_review → published → ongoing → ended → archived;任意非终态可 canceled。

- **创建**:两档——
  - **快速创建**:标题 + 时间 + 场地(30 秒完成);
  - **完整创建**:标题、起止时间与时区、人数建议、场地位置(**自运营场地**或**外部场地**)、交通路线、活动描述(富文本)、入场要求、Banner、是否付费(免费/定额/自愿付费)、报名表单问题、报名审批、容量、可见性、标签、Program 归属。
- **预览**:发布前只读渲染页。
- **发布**:触发——①单向同步 Luma ②单向同步 Social Layer ③通知(邮件 + 4seasbot)。
- **进行中**:二维码签到(主持人持码,扫一次变一次;一次性领取网址;数字上限——V2 接 NFT,见 07)、候补管理、改期通知。
- **结束**:自动归档、参与记录写入成员档案(V2 起同步 CAS 积分/NFT)。

### 5.3 Booking:场地预订

**两个入口,一个引擎**:

1. **随活动预订**:创建活动选择自运营场地时自动生成关联预订。
2. **独立预订入口**:会议、小组讨论等非公开活动直接订场地。

**预订状态机**:pending → approved / rejected;approved → checked_in → completed;非终态可 canceled。**积分字段全部预留但默认 0**——规则引擎的 points_per_hour 默认为 0,计费代码路径已实现但关闭, V2 开启。

**冲突检测**:场地 × 时间段(含缓冲)唯一性;容量校验;同成员同时段多预订软警告。

### 5.4 People:成员体系(经 CAS)

- **注册/验证/登录**:全部调用 CAS 接口(邮箱注册 → CAS 发验证邮件 → 验证后成为 Member)。本系统不存密码、不自主发验证邮件(邮件由 CAS 或邮件服务发出)。
- **资料镜像**:昵称、头像、时区等在本系统缓存镜像,CAS 为权威源。
- **Telegram 绑定**:经 CAS 完成绑定(initData 验证),本系统读绑定状态用于通知路由。
- **积分(镜像)**:CAS/链上为权威;本系统只读镜像展示,写入(预订扣减)通过 CAS 接口执行。**当前默认不收取任何积分。**
- **角色**:本地角色体系(Member/Host/Venue Manager/Admin),按场地/Program 授权。

### 5.5 通知系统

| 触发事件 | 邮件 | Telegram(经 4seasbot) | 站内 |
| --- | --- | --- | --- |
| 注册验证 | CAS 负责 | - | - |
| 活动发布 | 广播 | 群/频道推送 | 是 |
| 活动提醒(T-24h/T-1h) | 是 | 是 | 是 |
| 报名结果 | 是 | 是 | 是 |
| 活动改期/取消 | 是 | 是 | 是 |
| 预订审批结果 | 是 | 是(管理员审批入口) | 是 |
| 每日 digest | 是(可订阅) | 是(可订阅) | 是 |

机制:本系统产生通知事件 → 写入通知 outbox → 4seasbot 定时拉取并投递到 Telegram;邮件由本系统直接发。**Telegram Mini App(交互式报名/创建)二期实现,一期只做通知与指令。**

### 5.6 集成:对外分发

- **Luma(单向发布,M2)**:活动 published 时镜像创建/更新到 Luma;不回写报名数据(后续阶段);处理封面上传、限流、两步取消。
- **Social Layer(单向发布,M2)**:活动 published 时镜像创建到 sola.day(实测存在可用 API,见 04);兜底方案为 computer use。
- **4seasbot(通知)**:拉取式适配器,见 04。
- **Agent API(M2)**:REST + MCP,draft+confirm,独立 key 与审计。

## 6. 核心用户旅程

### 6.1 新成员加入

    收到活动链接 -> 打开活动页 -> 报名/注册
      -> CAS 完成邮箱注册与验证(邮件由 CAS 发出)
      -> 成为 Member -> (可选)经 CAS 绑定 Telegram
      -> 收到欢迎通知 -> 4seasbot 可向其推送活动提醒

### 6.2 成员发起活动(含场地)

    点击"创建活动" -> 快速创建(标题+时间+场地)
      -> 实时校验:场地可用性/冲突/规则(活动类型是否允许)
      -> 补充完整信息 -> 预览 -> 提交
      -> [如需审批] 场地管理员一键批准
      -> 发布:单向同步 Luma + Social Layer;邮件 + 4seasbot 通知
      -> 当天:主持人轮换二维码签到 -> 结束归档

### 6.3 独立预订场地(会议/讨论)

    选场地 -> 选时段(含缓冲显示)-> 填用途/人数 -> 提交
      -> 审批(自动或人工)-> 确认通知(邮件 + Telegram + .ics)
      -> 使用/取消按政策处理(积分预留,当前为 0)

### 6.4 Agent 创建活动(机器旅程)

    Agent 调用 search_venues / check_availability(直接执行)
      -> create_event_draft(返回草稿,无副作用)
      -> 人类在后台确认(或白名单策略自动确认)
      -> confirm -> 正式创建并触发与 6.2 相同的发布链路

## 7. 功能优先级(MoSCoW,v2)

### Must(MVP)

- CAS 对接:注册/验证/登录/会话、用户信息镜像
- 建筑/楼层/场地 CRUD + 基础信息 + 状态
- 场地规则配置(活动类型白名单、申请流程、提前窗口、取消政策、禁止行为;积分价字段预留默认 0)
- 活动快速/完整创建、状态机
- 随活动预订 + 独立预订、冲突检测、审批
- 邮件通知(发布、提醒、预订结果;验证邮件由 CAS 负责)
- 4seasbot 出站 feed(活动数据 + 通知 outbox,供 bot 拉取)
- 运营后台(场地、预订总览、成员镜像、审批)

### Should(V1)

- Telegram Bot 侧适配(4seas-bot 增加 CommunityOS 数据源,拉取式)
- Luma 单向发布(字段映射、封面上传、限流、取消)
- 报名管理、二维码签到(基础版:轮换二维码 + 一次性领取网址 + 人数上限)
- 日程表多视图(日/周/列表/地图)
- 数据导出(CSV/JSON)

### Could(V2)

- Social Layer 单向发布(API 或 computer-use 兜底)
- Agent API MCP 完整工具集 + 审计界面
- 链上积分(CAS + 链):签到/host/志愿者/speaker 赚取,兑换场地/咖啡/住宿(见 07)
- NFT 签到签发(外部 NFT 系统对接,见 07)
- Telegram Mini App(完整创建/预订表单)
- Luma webhook 回写、徽章/成就、活动模板

### Won't(明确不做)

- 自建账户体系(归 CAS)
- 自建票务收款(用 Luma Stripe / Telegram Payments)
- 通用 IM(不自研聊天,走 4seasbot/Telegram)
- 一期不自建链上积分发放逻辑(权威在链上/CAS,本系统只镜像)

## 8. 关键设计决策(ADR 式摘要)

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 主数据源在 CommunityOS,外部平台为镜像 | 避免双写冲突;外部平台可替换 |
| D2 | Luma/Social Layer **先只做单向发布** | 降低一期复杂度;回写与冲突解决后置 |
| D3 | 身份/账户/积分/签到/NFT 归 CAS,本系统接口消费 | 账户是跨系统资产(活动、预订、coliving、residency 都要用),避免每个系统各建一套 |
| D4 | 邮箱为身份主键,验证后成为成员 | 通知可达性兜底;未来 CAS 增加链上地址登录 |
| D5 | 场地规则全部配置化 + 版本化 | 规则是社区可协商的层 |
| D6 | 积分当前默认 0,接口与数据模型预留 | 避免过早金融化;链上积分 V2 对接时无需改表 |
| D7 | 积分展示为"链上镜像",CAS/链上为权威 | 与 V2 链上积分体系一致,避免双权威 |
| D8 | 写操作 draft+confirm(API 层统一) | luma-mcp 安全基线 |
| D9 | Telegram 通知经 4seasbot 拉取式集成 | 复用既有服务与运维,不为通知新开推送链路 |
| D10 | Mini App 二期 | 一期用 Bot 命令 + Web 覆盖核心场景 |
| D11 | MVP 模块化单体,CAS 以客户端模块隔离 | 团队规模小;CAS 替换/升级不影响核心 |
| D12 | 审计日志覆盖所有写操作(人 + Agent) | 社区信任与追溯基础 |

## 9. 成功指标

| 指标 | 定义 | 目标(MVP 后 3 个月) |
| --- | --- | --- |
| 自发活动占比 | 成员自发活动 / 总活动 | ≥ 60%(对标 Social Layer 69.7%) |
| 场地利用率 | 已预订时长 / 可预订时长 | ≥ 40% |
| 验证成员转化率 | 注册后 7 天内完成验证比例 | ≥ 70% |
| 发布同步成功率 | published 活动成功同步外部平台比例 | ≥ 99% |
| 通知打开率 | 邮件打开 + Telegram 点击 | ≥ 45% |
| Agent 调用成功率 | confirm 后成功执行比例 | ≥ 99% |
