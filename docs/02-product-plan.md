# 02 · 产品规划

> 基于 01-research-benchmark.md 的调研结论,本文档给出 4Seas CommunityOS 的完整产品规划。

---

## 1. 产品定位

### 1.1 一句话定位

**4Seas CommunityOS:运营于物理世界的在地社区操作系统——管好场地(Place),驱动活动(Event),服务成员(People)。**

### 1.2 我们要解决的真问题

4Seas 在清迈运营多栋自运营建筑(Building F、4Seas Nimman 等),当前痛点:

1. **场地信息分散**:楼层、房间、设备、容量、开放时间靠口口相传或表格,没有单一事实源。
2. **场地使用无规则、无 trace**:谁能用、要不要审批、收多少积分、什么行为被禁止,靠临时协商;占用冲突靠运气。
3. **活动发起链路长**:一场成员自发活动要经过多次沟通才能定场地、发通知。
4. **对外分发靠手工**:活动信息要手工搬去 Luma / Social Layer,报名数据回不来。
5. **成员身份与贡献无沉淀**:谁参加了什么、贡献了多少,没有可携带的记录。

### 1.3 产品目标(12 个月)

| 目标 | 衡量 |
| --- | --- |
| 场地使用透明化 | 100% 自运营场地在系统内,占用可视(日程表/地图) |
| 活动发起低门槛 | 成员 3 分钟内完成最小活动创建(what/when/where) |
| 对外分发自动化 | 发布后自动同步 Luma 与 Social Layer,报名数据自动回流 |
| 成员运营闭环 | 邮箱注册 → 验证 → 预订/发起 → 签到 → 积分,全链路线上化 |
| Agent 可用 | 外部 Agent 可通过 MCP/REST 查询场地与活动、按 draft+confirm 流程创建 |

## 2. 目标用户与角色

| 角色 | 描述 | 关键权限 |
| --- | --- | --- |
| Visitor 访客 | 未注册/未验证 | 浏览公开活动页、报名公开活动(留邮箱即创建待验证账户) |
| Member 成员 | 邮箱已验证 | 发起活动、预订场地(按规则与积分)、报名、签到、收藏 |
| Host 活动发起人 | 成员默认身份,可被场地规则限制(如仅信任成员可发起付费活动) | 管理自己活动的报名、嘉宾名单、签到 |
| Venue Manager 场地管理员 | 管理特定建筑/场地 | 场地 CRUD、规则配置、预订审批、占用调整 |
| Admin 社区管理员 | 社区运营 | 全局配置、成员角色、积分发放、数据导出、集成管理 |
| Agent 智能体 | 外部 AI Agent(机器身份) | 按 scope 查询;创建类操作走 draft + confirm |

**角色模型要点**(借鉴 Social Layer):同一用户在不同上下文角色不同(如在 A 社区是成员、在 B 社区是管理员),权限按"社区 + 资源"判定,不做全局单角色。

## 5. 核心功能详述

### 5.1 Place:场地管理

**实体层级**:Building(建筑)→ Floor(楼层)→ Venue(房间/场地)。场地可挂多个空间单元(如 Event Space 的 A/B 区)。

**场地基础信息(CRUD)**:

- 名称、所属建筑/楼层、编号、物理地址与地理坐标
- 面积(㎡)、层高、容纳人数上限(按座位/站立两种口径)
- 设备清单(投影、音响、白板、桌椅、厨房、WiFi、停车等,可多选 + 备注)
- 基础服务(保洁、空调、安保、饮品等)
- 有效时间:开放时间段(按星期配置)、例外日期(节假日关闭)
- 封面图、照片集、平面图
- 状态:开放 / 维护中 / 停用

**场地规则(附加于场地,可版本化)**:

| 规则项 | 说明 |
| --- | --- |
| 允许的活动类型 | 会议 / 工作坊 / 课程 / 派对 / 展览 / 运动……(白名单,可限定规模) |
| 申请流程 | 自动通过 / 场地管理员审批 / 社区管理员审批;可按活动类型分别设定 |
| 积分消耗 | 每小时积分价(可按会员等级折扣);免费额度是否适用;押金(可退) |
| 提前预订窗口 | 最多提前 N 天预订;最短提前 N 小时 |
| 单次时长上限 / 每月时长上限 | 防囤积 |
| 缓冲时间 | 布置 + 撤场分钟数(自动占用) |
| 取消政策 | 提前多久免费取消,逾期扣积分比例 |
| 禁止行为 | 明示条款(禁烟、禁过夜、噪音时段、禁止商业售卖等),违反记入信用 |
| 准入要求 | 仅验证成员 / 仅特定角色 / 公开 |

**原则**:规则是"可编辑的层"(Social Layer),不是硬编码;规则变更留存版本历史,不影响已确认预订。

### 5.2 Event:活动生命周期

**状态机**(详见 03-domain-model.md):

```
draft ──预览──► preview ──提交──► pending_review ──通过──► published ──开始──► ongoing ──结束──► ended ──归档──► archived
  │                │                   │                             │
  └── 任意状态可取消 ─┴─────────────────┴───────── cancel ───────────┘
```

- **创建**:两档——
  - **快速创建**:标题 + 时间 + 场地(3 个字段,30 秒完成),用于自发小型活动;
  - **完整创建**:标题、起止时间与时区、人数建议、场地位置(**自运营场地**或**外部场地**)、交通路线(地图/文字/公共交通指引)、活动描述(富文本)、入场要求(年龄/装备/提前阅读/审核)、Banner 封面、是否付费(免费 / 定额 / 自愿付费)、报名表单问题、是否需报名审批、容量、可见性、标签、Program 归属。
- **预览**:发布前的只读渲染页,确认外部平台(如 Luma)呈现效果。
- **发布**:触发三件事——①同步 Luma ②同步 Social Layer ③通知(邮件 + Telegram + 站内)。
- **进行中**:二维码签到、候补管理、改期(通知所有报名者)。
- **结束**:自动归档、参与记录写入成员档案、积分结算(发起人奖励、参与者奖励)。

### 5.3 Booking:场地预订

**两个入口,一个引擎**:

1. **随活动预订**:创建活动选择自运营场地时,自动生成关联预订,走同一规则引擎(审批、积分、冲突检测)。
2. **独立预订入口**:用于会议、小组讨论、自习等非公开活动——直接选场地、选时段、填用途、提交。

**预订状态机**:pending(待审批)→ approved / rejected;approved → checked_in(使用)→ completed;任意非终态可 canceled(按取消政策扣/退积分)。

**冲突检测**:场地 × 时间段(含缓冲时间)唯一性;容量校验(报名人数 ≤ 场地容量上限);同成员同时间段多预订告警。

### 5.4 People:成员体系

- **注册**:邮箱为唯一身份主键(通知账户)。注册即创建 unverified 账户。
- **邮箱验证**:发送带 token 的验证链接(24 小时有效、一次性),点击后成为 verified Member,获得成员权限(发起活动、预订场地)。
- **资料**:昵称、头像、简介、Telegram 绑定(initData 验证)、兴趣标签、时区。
- **角色**:见第 2 节;支持按场地/Program 授权。
- **积分(Points)**:
  - **获得**:月度额度(按会员等级,借鉴 Cobot)、发起活动奖励、被签到参与奖励、社区贡献(管理员手工发放)。
  - **消耗**:场地预订(按场地时价 × 时长)、付费活动票(可选)。
  - **账本**:每一笔变动双记录(账户流水 + 全局流水),可追溯、可导出;支持冻结、过期(如季度清零)。

### 5.5 通知系统

| 触发事件 | 邮件 | Telegram | 站内 |
| --- | --- | --- | --- |
| 注册验证 | ✓(必须) | - | - |
| 邮箱验证成功/欢迎 | ✓ | ✓(若已绑定) | ✓ |
| 活动发布 | ✓(广播) | ✓(频道/群) | ✓ |
| 活动提醒(前 24h / 1h) | ✓ | ✓ | ✓ |
| 报名成功 / 待审批 / 被拒 | ✓ | ✓ | ✓ |
| 活动改期/取消 | ✓ | ✓ | ✓ |
| 预订提交 / 审批结果 | ✓ | ✓(管理员审批入口) | ✓ |
| 积分到账 / 消耗 | ✓(汇总) | ✓ | ✓ |
| 每日日程 digest(可订阅) | ✓ | ✓ | ✓ |

规则:邮件为兜底通道(必须送达),Telegram 为即时通道(用户可绑定),站内为存档;所有通知在"通知中心"可查,偏好可配置。

### 5.6 集成:对外分发与双向回流

详见 04-integrations.md。摘要:

- **Luma**:活动发布时镜像创建/更新(主数据源在我方);Luma webhook 回写报名/取消;取消走两步确认;封面预上传 CDN;限流退避。
- **Social Layer**:4Seas 当前已在用(sola.day)。方案 A(首选):若开放 API,同样镜像同步;方案 B(过渡):保留 sola.day 页面 + 我们提供 iCal 订阅与嵌入组件,引导迁移。
- **Telegram**:Bot + Mini App,作为成员的第二界面与通知通道。
- **Agent API**:REST + MCP,draft+confirm,独立 key 与审计。

## 6. 核心用户旅程

### 6.1 新成员加入

```
收到活动链接/海报 → 打开活动页 → 点击报名/注册
  → 输入邮箱 → 收到验证邮件 → 点击验证链接 → 成为 Member
  → (可选)绑定 Telegram → 进入社区群 → 收到欢迎邮件 + 新手指引
```

### 6.2 成员发起活动(含场地)

```
Web/Mini App 点击"创建活动"
  → 快速创建:标题 + 时间 + 场地(或外部场地)
  → 系统实时校验:场地可用性 / 冲突 / 积分余额 / 规则(活动类型是否允许)
  → 补充完整信息(描述、banner、人数、入场要求、是否付费)
  → 预览 → 提交
  → [如需审批] 场地管理员在 Telegram/后台一键批准
  → 发布:自动同步 Luma + Social Layer,邮件 + Telegram 通知订阅者
  → 活动当天:二维码签到 → 结束后自动归档、积分入账
```

### 6.3 独立预订场地(会议/讨论)

```
选择场地 → 选择时段(日历视图,显示缓冲与占用)
  → 填用途/人数 → 提交(按规则:自动通过或转审批)
  → 审批通过 → 冻结/扣减积分 → 收到确认(邮件 + Telegram,含日历文件 .ics)
  → 使用当天签到 → 结束释放;未使用按取消政策处理
```

### 6.4 Agent 创建活动(机器旅程)

```
Agent 调用 search_venues / check_availability(直接执行)
  → create_event_draft(返回草稿,不落库为正式活动)
  → 人类在后台/Telegram 确认(或策略自动确认白名单 Agent)
  → confirm → 正式创建并触发与 6.2 相同的发布链路
```

## 7. 功能优先级(MoSCoW)

### Must(MVP)

- 邮箱注册 + 验证、基础资料、Telegram 绑定
- 建筑/楼层/场地 CRUD + 基础信息 + 状态
- 场地规则配置(活动类型白名单、申请流程、积分价、提前窗口、取消政策、禁止行为)
- 活动快速/完整创建、状态机(draft→preview→published→ended)
- 随活动预订 + 独立预订、冲突检测、审批
- 积分账本(发放/扣减/流水)
- 邮件通知(验证、发布、提醒、预订结果)
- 运营后台(场地、预订总览、成员、审批)

### Should(V1)

- Telegram Bot(创建引导、报名、审批、提醒、每日 digest)
- Luma 同步(发布镜像 + webhook 回写 + 对账)
- 报名管理、二维码签到、候补
- 日程表多视图(日/周/列表/地图)
- 数据导出(CSV/JSON)

### Could(V2)

- Social Layer 同步 / iCal 订阅
- Agent API MCP 完整工具集 + 审计界面
- 徽章/成就系统(参与凭证)
- 活动模板与重复活动
- 场地使用分析看板(利用率、热力图)

### Won't(明确不做)

- 自建票务收款(用 Luma Stripe / Telegram Payments)
- 通用 IM(不自研聊天,集成 Telegram/Discord)
- 区块链身份(保持邮箱中心,保留徽章导出能力即可)

## 8. 关键设计决策(ADR 式摘要)

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 主数据源在 CommunityOS,Luma/Social Layer 为镜像 | 避免双写冲突;外部平台随时可替换 |
| D2 | 活动字段集对齐 Luma create API | 同步零信息损失;团队已有 Luma 使用习惯 |
| D3 | 邮箱为身份主键,Telegram 为绑定渠道 | 邮件可达性兜底;Telegram 不做独立账户(避免身份碎片) |
| D4 | 场地规则全部配置化 + 版本化 | Social Layer 经验:规则是社区可协商的层 |
| D5 | 积分 = 内部账本,不与法币强绑定(预留) | 冷启动避免金融合规复杂度;Cobot 额度模型已验证产品形态 |
| D6 | 写操作 draft+confirm(API 层统一) | luma-mcp 安全基线;防止 Agent 误操作 |
| D7 | MVP 不引入微服务,模块化单体 + 明确模块边界 | 团队规模小,演进优先;模块边界保证未来可拆 |
| D8 | Web 用 PWA(可安装、可推送),Telegram Mini App 复用同一前端 | 一套前端多入口,降低维护成本 |
| D9 | 所有列表/日历接口提供 iCal 输出 | 数据可携带,兼容用户既有日历习惯 |
| D10 | 审计日志覆盖所有写操作(人 + Agent) | 社区信任与问题追溯的基础设施 |

## 9. 成功指标

| 指标 | 定义 | 目标(MVP 后 3 个月) |
| --- | --- | --- |
| 自发活动占比 | 成员自发活动 / 总活动 | ≥ 60%(对标 Social Layer 69.7%) |
| 场地利用率 | 已预订时长 / 可预订时长 | ≥ 40% |
| 验证成员转化率 | 注册后 7 天内完成邮箱验证比例 | ≥ 70% |
| 预订冲突率 | 因冲突被拒的预订占比 | ≤ 5% |
| 通知打开率 | 邮件打开 + Telegram 点击 | ≥ 45% |
| Agent 调用成功率 | confirm 后成功执行比例 | ≥ 99% |
