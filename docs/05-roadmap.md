## 2. M0:地基(第 1-3 周)

**目标**:最小可运营——场地在线、活动能发、成员能验证。

范围:

- 技术底座:模块化单体、PostgreSQL、对象存储、事务邮件、任务队列、审计日志框架。
- People:邮箱注册、验证邮件(24h token)、magic link 登录、基础资料、Telegram 绑定(先存 ID,通知后置)。
- Place:建筑/楼层/场地 CRUD;场地基础信息(面积/设备/容量/开放时间);场地状态管理。
- Event:draft -> preview -> published -> ended 状态机;快速创建(标题/时间/场地)与完整创建;可见性。
- 运营后台雏形:场地列表、成员列表、活动列表。

验收标准:

- 管理员能在 10 分钟内完成一栋楼的建筑-楼层-场地录入。
- 新用户注册后收到验证邮件,点击后成为 Member。
- 成员创建活动并发布,公开页可访问,管理员收到通知。

---

## 3. M1:运营闭环(第 4-7 周)

**目标**:场地可订、积分可算、通知可达——社区日常运营可迁移上线。

范围:

- Booking:独立预订 + 随活动预订;冲突检测(含缓冲);审批(auto / venue_manager / admin);取消政策与押金。
- Points:积分账户、账本、月度额度(按 tier)、预订扣减/退还、手工调整(admin)。
- 场地规则:活动类型白名单、积分价、提前窗口、时长上限、禁止行为条款(预订时确认)。
- Notify:邮件通知全矩阵 + 站内通知中心;Telegram Bot 基础(绑定、审批按钮、活动提醒)。
- Schedule:日/周/列表视图;iCal 订阅输出。

验收标准:

- 成员可独立预订场地,管理员在 Telegram 内一键审批;冲突预订被系统拒绝。
- 积分流水完整可查;取消按政策正确退/扣。
- 一场活动从创建到发布到通知全流程无人工搬运。

---

## 4. M2:分发与 Agent(第 8-11 周)

**目标**:对外分发自动化,Agent 可查询与创建。

范围:

- Luma 集成:字段映射、发布镜像、封面上传、webhook 回写、对账任务、限流与重试、dead_letter 处理。
- Telegram 完善:Mini App(完整创建表单、预订日历)、每日 digest、群卡片。
- Agent API:REST v1(draft+confirm)+ MCP server(读工具 + 写工具对);key 管理、scope、审计界面。
- 报名管理:嘉宾名单、候补、二维码签到。

验收标准:

- 活动发布后 1 分钟内外部平台可见;Luma 报名 5 分钟内回流到我方。
- 外部 Agent 通过 MCP 完成"查场地 -> 草稿创建活动 -> 人类确认 -> 发布"全流程。
- 审计日志可回放任意一次 Agent 写操作。

---

## 5. M3:增强(第 12 周起,持续)

- Social Layer 同步(取决于 API 开放度,见开放问题 Q1)或 iCal/深链过渡方案。
- 徽章/参与凭证(参与记录导出为可验证凭证)。
- 活动模板与重复活动。
- 场地使用分析(利用率热力图、高峰时段、自发活动占比看板)。
- Program 维度运营(themed residency 支持)。
- 多语言(中/英)。

## 6. 成功指标与复盘节奏

| 阶段 | 关键指标 |
| --- | --- |
| M0 | 场地录入完成率、注册-验证转化率 |
| M1 | 周活跃预订数、冲突拒绝率、通知打开率 |
| M2 | 同步成功率(>99%)、webhook 回流延迟(P95 < 5min)、Agent confirm 率 |
| M3 | 自发活动占比(>60%)、场地利用率(>40%)、digest 打开率 |

每阶段结束做一次复盘:指标回顾 + 运营反馈收集 + 下阶段范围调整。

## 7. 风险与缓解

| 风险 | 影响 | 概率 | 缓解 |
| --- | --- | --- | --- |
| Luma Plus 订阅不可用或中途失效 | 同步功能降级 | 中 | 功能开关解耦;降级模式(仅站内);对账提示 |
| Social Layer 无开放写 API | 无法自动分发 | 中高 | 方案 B/C 过渡;iCal + 深链;长期谈合作 |
| 邮件到达率低(验证邮件进垃圾箱) | 注册转化崩坏 | 中 | 独立域名 + SPF/DKIM/DMARC;备选渠道(Telegram 验证码);监控退信率 |
| 社区运营流程迁移阻力(大家习惯微信/sola.day) | 采用率低 | 高 | 从 4Seas 现有活动与场地数据种子导入;指定 2-3 个"种子活动"首批迁移;保留 sola.day 只读页 |
| 积分体系设计不当引发公平争议 | 社区矛盾 | 中 | 规则透明 + 版本化 + 申诉通道;MVP 期积分只用于场地预订,不做强社交排名 |
| Agent 误操作/滥用 | 数据错乱 | 中 | draft+confirm、scope 最小化、限流、审计、一键吊销 |
| 单人/小团队交付压力 | 延期 | 中 | MVP 严格裁剪(见下);模块化单体避免过度设计 |
| 合规(个保法/GDPR:邮箱与出席数据) | 法务风险 | 低-中 | 数据导出/删除能力;隐私政策;最小化收集 |

---

## 8. 范围裁剪原则(防蔓延)

1. 每个阶段只做一个"不可逆"决策: M0 = 数据模型冻结;M1 = 积分规则冻结;M2 = 同步契约冻结。
2. 任何新需求进入下一阶段池,不在当期追加。
3. 付费收款不自建(始终用 Luma Stripe / Telegram Payments)。
4. 不做通用 IM、不做区块链身份(预留凭证导出)。
